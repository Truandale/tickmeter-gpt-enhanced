## Анализ метрик

### PING (Задержка)
- **Единицы**: миллисекунды (ms)
- **Нормальные значения**: 10-100ms
- **Что такое спайк**: резкое **УВЕЛИЧЕНИЕ** задержки
- **Направление детекции**: только возрастающие спайки
- **Формула**: `deviation = (current - EMA)`
- **Условие спайка**: `deviation > threshold` (положительное отклонение)

### TICKRATE (Частота обновлений)
- **Единицы**: Герцы (Hz) или тики/сек
- **Нормальные значения**: 20-128Hz (зависит от игры)
  - CS:GO: 64Hz или 128Hz
  - PUBG: 20-60Hz
  - Valorant: 128Hz
- **Что такое спайк**: резкое **СНИЖЕНИЕ** частоты (меньше тиков = хуже)
- **Направление детекции**: только падающие спайки
- **Формула**: `deviation = (EMA - current)` **(инверсия!)**
- **Условие спайка**: `deviation > threshold` (EMA больше current = падение)
- **Примеры проблемных спайков**:
  - Падение с 64Hz → 30Hz = критично
  - Падение с 128Hz → 80Hz = заметно
  - Кратковременное падение на 20+ Hz

### TICKTIME (Интервал между тиками)
- **Единицы**: миллисекунды (ms)
- **Нормальные значения**: 7-50ms
  - 128Hz → 7.8ms
  - 64Hz → 15.6ms
  - 20Hz → 50ms
- **Что такое спайк**: резкое **УВЕЛИЧЕНИЕ** интервала (больше время = хуже)
- **Направление детекции**: только возрастающие спайки (как ping)
- **Формула**: `deviation = (current - EMA)`
- **Условие спайка**: `deviation > threshold` (положительное отклонение)
- **Связь с tickrate**: `TickTime ≈ 1000 / TickRate`
- **Примеры проблемных спайков**:
  - Скачок с 15ms → 50ms = критично
  - Скачок с 15ms → 30ms = заметно

## Предлагаемые параметры пресетов

### Пресет: VERY_LOW (минимальная чувствительность)

**Цель**: Детектировать только критичные ситуации и быстро снимать при нормализации

| Метрика   | tauSec | minAbs  | minRel | kHi | kLo | Описание |
|-----------|--------|---------|--------|-----|-----|----------|
| **Ping**     | 10.0   | 40ms    | 1.2    | 5.0 | 0.5 | Только критические спайки >40ms, быстрое снятие |
| **Tickrate** | 10.0   | 25Hz    | 0.40   | 5.0 | **2.0** | Падение >25Hz или >40%, **умеренное снятие** |
| **Ticktime** | 10.0   | 25ms    | 1.0    | 5.0 | **1.0** | Увеличение >25ms или >100%, **умеренное снятие** |

**Ключевые особенности**:
- **kLo для tickrate выше (2.0)**: чтобы спайк снимался при частичном восстановлении (не требует полной нормализации)
- **kLo для ticktime выше (1.0)**: чтобы снятие происходило при умеренном улучшении
- **minAbs масштабирован**: 40ms для ping, 25ms для ticktime (адекватно для масштаба метрики)
- **minRel для tickrate 0.40 (40%)**: только серьезные падения (64Hz → 38Hz)

**Когда использовать**: Стабильные сети, не хотите ложных срабатываний, но нужна быстрая реакция на критичные проблемы

---

### Пресет: LOW (низкая чувствительность)

**Цель**: Детектировать серьезные проблемы, игнорируя мелкие колебания

| Метрика   | tauSec | minAbs  | minRel | kHi | kLo | Описание |
|-----------|--------|---------|--------|-----|-----|----------|
| **Ping**     | 8.0    | 25ms    | 0.8    | 4.0 | 1.0 | Спайки >25ms или >80% роста |
| **Tickrate** | 8.0    | 18Hz    | 0.30   | 4.0 | **1.5** | Падение >18Hz или >30% |
| **Ticktime** | 8.0    | 18ms    | 0.7    | 4.0 | **1.2** | Увеличение >18ms или >70% |

**Анализ работы**:
- **kLo для tickrate 1.5**: умеренное снятие, не требует почти полного восстановления
- **kLo для ticktime 1.2**: чуть быстрее чем tickrate (промежуточное между ping и tickrate)
- **minAbs масштабирован**: 25ms для ping, 18ms для ticktime (адекватно для метрики)
- **minRel для tickrate 0.30**: падение на 30% уже серьезная проблема (64Hz → 45Hz)

**Когда использовать**: Обычная игра, средняя стабильность сети, не хотите частых срабатываний

---

### Пресет: MEDIUM (средняя чувствительность) - **ПО УМОЛЧАНИЮ**

**Цель**: Оптимальный баланс - детектировать значимые проблемы без ложных срабатываний

| Метрика   | tauSec | minAbs  | minRel | kHi | kLo | Описание |
|-----------|--------|---------|--------|-----|-----|----------|
| **Ping**     | 6.0    | 15ms    | 0.6    | 3.0 | 1.5 | Спайки >15ms или >60% роста |
| **Tickrate** | 6.0    | 12Hz    | 0.22   | 3.0 | **1.8** | Падение >12Hz или >22% |
| **Ticktime** | 6.0    | 12ms    | 0.55   | 3.0 | **1.6** | Увеличение >12ms или >55% |

**Анализ работы**:
- **kLo для tickrate 1.8**: баланс между быстрым и умеренным снятием
- **kLo для ticktime 1.6**: чуть быстрее снятие чем у tickrate
- **minAbs масштабирован**: 15ms для ping, 12ms для ticktime
- **minRel для tickrate 0.22**: падение на 22% заметно (64Hz → 50Hz, 128Hz → 100Hz)

**Примеры работы**:
```
CS:GO 64Hz → падение до 48Hz (падение 25%)
→ Детектируется как спайк ✅
→ Восстановление до 58Hz (91%)
→ Быстрое снятие ✅

PUBG ping 40ms → скачок до 65ms (рост 62%)
→ Детектируется как спайк ✅
→ Снижение до 50ms
→ Быстрое снятие ✅
```

**Когда использовать**: Рекомендуется для большинства пользователей - баланс между чувствительностью и стабильностью

---

### Пресет: HIGH (высокая чувствительность)

**Цель**: Детектировать даже небольшие проблемы, максимальная информативность

| Метрика   | tauSec | minAbs  | minRel | kHi | kLo | Описание |
|-----------|--------|---------|--------|-----|-----|----------|
| **Ping**     | 4.0    | 10ms    | 0.4    | 2.5 | 1.8 | Даже небольшие спайки >10ms или >40% |
| **Tickrate** | 4.0    | 8Hz     | 0.15   | 2.5 | **2.0** | Падение >8Hz или >15% |
| **Ticktime** | 4.0    | 8ms     | 0.38   | 2.5 | **1.9** | Увеличение >8ms или >38% |

**Анализ работы**:
- **kLo для tickrate 2.0**: относительно высокий, чтобы избежать "мигания" индикатора при высокой чувствительности
- **kLo для ticktime 1.9**: близко к ping, но чуть медленнее снятие
- **minAbs масштабирован**: 10ms для ping, 8ms для ticktime (детектирует малые отклонения)
- **minRel для tickrate 0.15**: даже 15% падение детектируется (64Hz → 54Hz, 128Hz → 109Hz)

**Примеры работы**:
```
CS:GO 128Hz → падение до 109Hz (падение 15%)
→ Детектируется ✅ (при medium не детектировалось бы)

CS:GO ticktime 7.8ms → рост до 16ms (рост 105%)
→ Детектируется ✅

Ping 25ms → рост до 36ms (рост 44%)
→ Детектируется ✅ (при medium не детектировалось бы)
```

**Предупреждение**: Возможны частые срабатывания на нестабильных сетях!

**Когда использовать**: Соревновательная игра, диагностика проблем сети, высокие требования к качеству соединения

---

### Пресет: AUTO (адаптивный)

**Начинает с MEDIUM**, затем адаптируется на основе наблюдаемого поведения:

| Условие | Действие | Обоснование |
|---------|----------|-------------|
| **Много ложных срабатываний** (>20 спайков/мин) | Понижает до LOW → VERY_LOW | Сеть нестабильная, но это норма для данного подключения |
| **Стабильная сеть** (σ < 10% от μ на протяжении 5 минут) | Понижает до LOW → VERY_LOW | Сеть хорошая, нужны только критичные предупреждения |
| **Частые реальные проблемы** (детектированы спайки >2x порога) | Повышает до HIGH | Нужна максимальная информативность |
| **После изменения адаптера** | Сброс на MEDIUM | Новые условия сети, повторная калибровка |

**Особенности AUTO режима**:
```csharp
// Адаптация параметров в реальном времени
if (spikesPerMinute > 20) {
    // Слишком много срабатываний - понижаем чувствительность
    currentSensitivity = Math.Max(currentSensitivity - 1, VERY_LOW);
} 
else if (avgStdDev / avgMean < 0.10 && stableDuration > 5min) {
    // Стабильная сеть - можно понизить
    currentSensitivity = VERY_LOW;
}
else if (criticalSpikesDetected > 3 in lastHour) {
    // Есть реальные проблемы - повышаем чувствительность
    currentSensitivity = Math.Min(currentSensitivity + 1, HIGH);
}
```

**Когда использовать**: 
- Не уверены в качестве своего подключения
- Хотите автоматической оптимизации
- Часто переключаетесь между сетями (Wi-Fi ↔ Ethernet ↔ VPN)

## Ключевые закономерности в параметрах

### 1. **tauSec (постоянная времени EMA)**
```
VERY_LOW: 10s → медленная адаптация, игнорирует краткосрочные колебания
LOW:      8s  → умеренная адаптация
MEDIUM:   6s  → сбалансированная адаптация (по умолчанию)
HIGH:     4s  → быстрая адаптация, реагирует на малые изменения
```
**Одинаково для всех метрик** - определяет "инерцию" базовой линии

### 2. **kHi (порог начала спайка)**
```
VERY_LOW: 5.0σ → очень высокий, только экстремальные отклонения
LOW:      4.0σ → высокий
MEDIUM:   3.0σ → средний (стандарт в статистике)
HIGH:     2.5σ → низкий, чувствительный
```
**Одинаково для всех метрик** - определяет "что считается спайком"

### 3. **kLo (порог снятия спайка) - АДАПТИВНЫЙ!**

#### Для PING:
```
VERY_LOW: 0.5σ → очень быстрое снятие (пинг быстро стабилизируется)
LOW:      1.0σ → быстрое снятие
MEDIUM:   1.5σ → умеренное снятие
HIGH:     1.8σ → медленное снятие (избегаем "мигания" при высокой чувствительности)
```

#### Для TICKRATE (требует БОЛЕЕ ВЫСОКИЙ kLo):
```
VERY_LOW: 2.0σ → не требует полного восстановления (60Hz из 64Hz уже OK)
LOW:      1.5σ → умеренное требование к восстановлению
MEDIUM:   1.8σ → баланс
HIGH:     2.0σ → высокий, чтобы избежать "мигания" при частых малых колебаниях
```

#### Для TICKTIME (промежуточное значение):
```
VERY_LOW: 1.0σ → умеренное снятие
LOW:      1.2σ → чуть медленнее
MEDIUM:   1.6σ → баланс
HIGH:     1.9σ → близко к ping, но учитываем связь с tickrate
```

**Почему разные?**
- **Ping**: быстро меняется и стабилизируется → низкий kLo
- **Tickrate**: медленно восстанавливается, частичное восстановление приемлемо → высокий kLo
- **Ticktime**: коррелирует с tickrate, но чуть более отзывчив → средний kLo

### 4. **minAbs (абсолютный минимум) - МАСШТАБИРОВАН!**

#### Для PING (ms):
```
VERY_LOW: 40ms → только критичные лаги
LOW:      25ms → серьезные лаги
MEDIUM:   15ms → заметные лаги
HIGH:     10ms → даже небольшие лаги
```

#### Для TICKRATE (Hz):
```
VERY_LOW: 25Hz → критичное падение (64→39Hz)
LOW:      18Hz → серьезное падение (64→46Hz)
MEDIUM:   12Hz → заметное падение (64→52Hz)
HIGH:     8Hz  → даже малое падение (64→56Hz)
```

#### Для TICKTIME (ms):
```
VERY_LOW: 25ms → критичный рост интервала
LOW:      18ms → серьезный рост
MEDIUM:   12ms → заметный рост
HIGH:     8ms  → даже малый рост
```

**Соотношение**: minAbs(ticktime) ≈ minAbs(ping) * 0.6-0.7 (масштаб метрики)

### 5. **minRel (относительный порог) - АДАПТИВНЫЙ!**

#### Для PING (%):
```
VERY_LOW: 120% → удвоение и более (30ms → 66ms)
LOW:      80%  → существенный рост (30ms → 54ms)
MEDIUM:   60%  → заметный рост (30ms → 48ms)
HIGH:     40%  → даже малый рост (30ms → 42ms)
```

#### Для TICKRATE (%) - БОЛЕЕ ЧУВСТВИТЕЛЬНЫЙ:
```
VERY_LOW: 40% → критичное падение (64Hz → 38Hz)
LOW:      30% → серьезное падение (64Hz → 45Hz)
MEDIUM:   22% → заметное падение (64Hz → 50Hz)
HIGH:     15% → даже малое падение (64Hz → 54Hz)
```

#### Для TICKTIME (%):
```
VERY_LOW: 100% → удвоение (15ms → 30ms)
LOW:      70%  → существенный рост (15ms → 25.5ms)
MEDIUM:   55%  → заметный рост (15ms → 23.3ms)
HIGH:     38%  → даже малый рост (15ms → 20.7ms)
```

**Почему tickrate более чувствителен?**
Падение tickrate на 20-30% критичнее для геймплея, чем рост ping на 60-80%!

## Почему разные kLo для разных метрик?

### Проблема с единым kLo
Если использовать `kLo = 0.5` (как для ping) для всех метрик:

**Ping** (работает отлично):
```
EMA = 30ms, σ = 5ms
Начало спайка: ping > 30 + 5.0*5 = 55ms
Снятие спайка: ping < 30 + 0.5*5 = 32.5ms
→ Быстрое снятие при падении до ~33ms ✅
```

**Tickrate** (проблема!):
```
EMA = 64Hz, σ = 3Hz
Начало спайка: tickrate < 64 - 5.0*3 = 49Hz (падение)
Снятие спайка: tickrate > 64 - 0.5*3 = 62.5Hz
→ Требует почти полного восстановления! ❌
```

Если tickrate упал с 64Hz до 45Hz (серьезная проблема), то:
- Спайк детектируется ✅
- Но снимется только при восстановлении до 62.5Hz
- Промежуточное состояние 50-55Hz (уже приемлемо) не снимет индикатор! ❌

### Решение: Адаптивный kLo

**Для PING**: `kLo = 0.5` (низкий, быстрое снятие)
- Пинг быстро нормализуется
- Кратковременные спайки должны быстро пропадать

**Для TICKRATE**: `kLo = 2.0` (средний, умеренное снятие)
- Tickrate восстанавливается медленнее
- Частичное восстановление (50Hz → 55Hz) уже приемлемо
- Не требуем полной нормализации до EMA

**Для TICKTIME**: `kLo = 1.0` (средний, умеренное снятие)
- Баланс между ping и tickrate
- Ticktime коррелирует с tickrate, восстанавливается постепенно

### Пример работы с новыми параметрами

**VERY_LOW для Tickrate**:
```
Игра: CS:GO, нормальный tickrate = 64Hz
EMA = 64Hz, σ = 2Hz

1. Потеря пакетов → tickrate падает до 38Hz
   deviation = 64 - 38 = 26Hz
   threshold = max(25Hz, 0.40*64=25.6Hz, 5.0*2=10Hz) = 25.6Hz
   26Hz > 25.6Hz → СПАЙК ДЕТЕКТИРОВАН ✅

2. Частичное восстановление → tickrate = 55Hz
   deviation = 64 - 55 = 9Hz
   lowerThreshold = 2.0 * 2Hz = 4Hz
   9Hz > 4Hz → спайк продолжается (это правильно, 55Hz еще низко)

3. Дальнейшее восстановление → tickrate = 60Hz
   deviation = 64 - 60 = 4Hz
   lowerThreshold = 4Hz
   4Hz <= 4Hz → СПАЙК СНЯТ ✅
   
Результат: Спайк снялся при 60Hz (93% от нормы), не требуя 
          полного восстановления до 64Hz. Быстрое снятие! ✅
```

## Ключевые отличия в реализации

### 1. Направление детекции

```csharp
// PING и TICKTIME - детектируем РОСТ
double deviation = current - EMA;
bool isSpike = deviation > threshold;

// TICKRATE - детектируем ПАДЕНИЕ (инверсия!)
double deviation = EMA - current;  // ← обратный порядок!
bool isSpike = deviation > threshold;
```

### 2. Масштабирование порогов

```csharp
// Для Tickrate - порог масштабируется к ожидаемым значениям игры
double expectedTickrate = 64.0; // из профиля игры
double scaledThreshold = baseThreshold * (EMA / expectedTickrate);
```

### 3. Минимальные значения

```csharp
// PING: спайк если ping > μ + threshold
// TICKTIME: спайк если ticktime > μ + threshold  
// TICKRATE: спайк если tickrate < μ - threshold (меньше!)
```

## Математическое обоснование параметров

### Почему именно эти значения?

#### minAbs (Абсолютный порог)
- **Ping**: 15ms = типичная задержка Wi-Fi → LAN
- **Tickrate**: 10Hz = примерно 15% падение от 64Hz tickrate
- **Ticktime**: 10ms = удвоение интервала с 15ms до 25ms

#### minRel (Относительный порог)
- **Ping**: 0.6 = 60% увеличение (30ms → 48ms считается спайком)
- **Tickrate**: 0.20 = 20% падение (64Hz → 51Hz считается спайком)
- **Ticktime**: 0.5 = 50% увеличение (15ms → 22.5ms считается спайком)

**Почему tickrate более чувствителен?**
Падение tickrate на 20% гораздо заметнее в геймплее, чем увеличение ping на 60%.

#### kHi / kLo (Множители стандартного отклонения)
- **kHi**: порог для **начала** спайка
- **kLo**: порог для **конца** спайка (гистерезис)
- Разница предотвращает "мигание" индикатора

## Примеры работы

### Пример 1: Стабильная игра (CS:GO 64 tick)
```
TickRate EMA: 64Hz, σ=2Hz
Current: 62Hz
deviation = 64 - 62 = 2Hz
threshold = max(10Hz, 0.20*64Hz=12.8Hz, 3.0*2Hz=6Hz) = 12.8Hz
2Hz < 12.8Hz → НЕТ СПАЙКА
```

### Пример 2: Потеря пакетов (CS:GO 64 tick)
```
TickRate EMA: 64Hz, σ=2Hz
Current: 45Hz (потеря пакетов!)
deviation = 64 - 45 = 19Hz
threshold = 12.8Hz
19Hz > 12.8Hz → СПАЙК ДЕТЕКТИРОВАН! ✓
```

### Пример 3: Кратковременный лаг тиктайма (PUBG)
```
TickTime EMA: 30ms, σ=3ms
Current: 55ms (задержка!)
deviation = 55 - 30 = 25ms
threshold = max(10ms, 0.5*30ms=15ms, 3.0*3ms=9ms) = 15ms
25ms > 15ms → СПАЙК ДЕТЕКТИРОВАН! ✓
```
